# Inquiry operations

The public website also supports OKKI automatic binding for ordinary inquiry forms. See [小满接入与验证](okki-inquiries.md) for the production-domain gate, field mapping, Chatbox exclusion, and the limits of browser capture. CMS persistence and its saved-record receipt remain independent of third-party tracking.

The browser submits through the Next.js inquiry endpoint. Next sends the private `STRAPI_SERVER_TOKEN` credential to `POST /api/inquiries/submit`; it never exposes that credential to the browser. This is an application service credential, not an admin API token from the Strapi UI. The CMS route has `auth: false` because its custom policy authenticates this credential before using the Next-supplied `X-Inquiry-Client` visitor IP. Invalid forwarded IPs fall back to the CMS request IP. Keep Next and Strapi behind the trusted reverse proxy described in the deployment documentation.

The policy allows five authenticated submissions per visitor IP per 60 seconds. Counters are local to one CMS process and reset on restart; multiple CMS instances need a shared limiter before scaling. Rejected credentials do not consume the visitor's quota. Field validation and the honeypot run before saving. Only normalized name, email, whatsapp, country, productType, quantity, message and source are accepted. Caller-supplied internal notes, business status, proof and arbitrary fields are never stored. The service sets `followUpStatus: new`; the receipt is `{ "id": "saved-document-id", "status": "received" }` only after persistence returns an identifier. A receipt acknowledges storage, not a quotation or notification.

The floating Chatbox collects a visitor's conversation before explicitly requesting contact details. Sources beginning `chatbox:` accept an email or an international WhatsApp number; supplied contacts must all pass format checks. WhatsApp formatting spaces, parentheses, dots and hyphens are removed; the stored number uses a `+` country code with 7–15 digits. Name, country and message remain required, and standard inquiries still require email. A phone-only chat inquiry stores a null email rather than fabricating one. Format validation does not verify contact ownership or reachability. The source includes language and page path; `message` holds the visitor's submitted messages. Typing, sending an initial chat message and minimizing the window do not create a backend record.

Sales reviews Chatbox leads in the existing Content Manager → Inquiry list, filtering `source` to start with `chatbox:`. New Sales roles can read the WhatsApp field; existing customized roles are preserved and require a super administrator to grant that field if needed. The administrator can also add `whatsapp`, `source` and `followUpStatus` to the list layout. Contact/message fields remain read-only for Sales. There is no automated email/WhatsApp notification or real-time agent conversation. Preview routes and `SITE_PREVIEW_MODE=true` simulate submission and explicitly say that nothing is saved. Deploy CMS and Web together to enable phone-only leads.

Responses use 400 for invalid fields or rejected/missing challenge proof, 401 for an invalid service credential, 429 for rate limiting, 503 for incomplete challenge configuration and 502 for database/upstream failure. Provider diagnostics and secrets are not returned. SMTP and notifications are outside this slice. Inquiry has no public list, read, update or delete routes, and accepts no customer attachments.

The product-direction selector uses published products for the page's language. When that list is empty, it offers bilingual general inquiry directions: folding home, flat-pack home, detachable office and other/custom project. These save as `folding-home`, `flat-pack-home`, `detachable-office` and `custom-project` in `productType`. Publishing translated products automatically replaces the general choices with that language's product list. The field remains optional.

A network interruption can happen after the CMS saves the record but before the browser receives its receipt. Check Content Manager before resubmitting to avoid duplicate follow-up. This slice has no submission deduplication, CRM assignment, bulk export or automatic WhatsApp/email messages. Process new inquiries by creation time; PostgreSQL volumes retain the development records, while formal backup/restore procedures belong to deployment.

## Optional Turnstile

Leave both `TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY` absent to disable verification. Enabling it requires the same public site key at Next runtime and CMS runtime, and the secret key **only at the CMS**. Setting only one CMS key fails closed. Set `TURNSTILE_EXPECTED_HOSTNAME` in the CMS when submissions must originate from one configured host.

The widget uses action `inquiry`; Next forwards its proof as `turnstileToken`. CMS calls Cloudflare Siteverify over HTTPS with the secret, proof, and a validated visitor IP when available, using a five-second timeout. It requires `success: true`, action `inquiry` and the configured hostname when present. Proof must be nonempty and at most 2048 characters, is never persisted, and rejected, expired or duplicate proofs never produce a saved receipt. Network, malformed JSON or HTTP upstream failures cannot bypass verification. [Cloudflare documents single-use proofs and five-minute expiry](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/). The frontend must reset its widget after submission/rejection; enabling keys also requires the Task 5 frontend widget and forwarding implementation.

## Admin roles and daily use

Bootstrap creates **Operations** (`modular-operations`) and **Sales** (`modular-sales`) admin roles with initial grants, without creating or assigning any user accounts. Role creation and initial permission assignment share a database transaction. Existing roles with these codes are preserved on later boots, including manual permission customizations. A conflicting unrelated role name makes initial creation fail; resolve the name in the admin UI instead of adopting an unknown role automatically.

These are Strapi **admin RBAC** roles for Content Manager, not Content API login roles. The users-permissions plugin is not installed. Explicit published-only GET routes provide anonymous public content reads; public write permissions are not needed.

| Role | Allowed | Excluded from initial grants |
| --- | --- | --- |
| Operations | Create/read/update/delete/publish Products, Project Cases, Articles, Certificates, FAQs and Site Settings; upload/read/edit/replace/delete public media | Inquiries, admin users/roles/tokens, locale administration, upload/infrastructure settings |
| Sales | Read inquiries and private internal notes; update only followUpStatus and internalNotes | Inquiry creation/deletion/publication, changes to contact/message fields, public content, media and infrastructure settings |

In pinned Strapi 5.57, media `assets.update` includes delete. Only public website assets belong in this media library; its permissions do not enforce a separate private bucket/prefix. Keep customer attachments excluded. A narrow application guard adds the project-settings permission to the otherwise authentication-only `PUT /i18n/settings` write route. Initial custom-role grants exclude that action; Super Admin retains access.

A super administrator creates/invites real users in `/admin` and assigns only the required role. Admin permissions combine across every assigned role: adding Editor, Author or Super Admin can bypass these role boundaries. Verify each account's complete role membership. Initial Operations grants include only the locale codes configured when the role is first created. When adding a language, a super administrator must update the Operations role's locale scope for all five public-content actions. Startup deliberately preserves those subsequent choices.

Sales opens Inquiry in Content Manager, reviews the contact details/message, and edits **followUpStatus** and **internalNotes**. The allowed workflow values are new, qualified, quoted, won and lost. `internalNotes` stays private to the backend. Strapi reserves `status` for draft/publication metadata, which is why the sales field is named `followUpStatus`.

## Existing-database migration and acceptance

The application includes `apps/cms/database/migrations/2026.10.10T00.00.00.inquiry-follow-up-status.js`. Keep this raw directory in the production image: Strapi discovers user migrations from the application-root `database/migrations`, not TypeScript output. At startup, before schema synchronization, the migration renames `inquiries.status` to `inquiries.follow_up_status` when the old column exists and the target does not. PostgreSQL retains the existing values. Fresh and already migrated databases require no rename. If both columns exist, startup stops for operator reconciliation instead of discarding values. Rollback requires restoring the database backup with the matching prior CMS version; the migration does not offer an automatic destructive down operation. Back up PostgreSQL before the first deployment. Previously customized inquiry role grants or saved Content Manager layouts that reference the old field must be updated by a super administrator.

Local tests exercise compiled controllers/services and real Strapi policy middleware, admin action registration, permission assignment, permission engine, Content Manager sanitizers/document metadata, and migration discovery/resolver/runner. Database and Cloudflare boundaries are doubled. Real PostgreSQL migration, new-role creation, browser admin editing and S3 persistence still require VM acceptance; none is claimed by these unit/integration tests.

On the Linux VM, after an authorized deployment and human admin setup, check: a valid inquiry survives a CMS restart; a honeypot/invalid challenge saves nothing; a sixth rapid request returns 429; Sales can read and update follow-up status/notes while forged contact/message edits are stripped; Operations can publish each public type and upload/delete a website image; Sales cannot access media; neither account can write upload/i18n/infrastructure settings. Confirm old inquiry statuses survived the migration. Account creation and VM changes are manual deployment steps, not part of this implementation.
